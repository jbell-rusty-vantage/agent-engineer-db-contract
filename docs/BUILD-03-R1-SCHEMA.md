## A. Model in one paragraph

A learner starts an **attempt** at an exact task revision under declared conditions (purpose, assistance facet, allowed tools/models). Finishing produces a **submission**: a frozen, digest-verified set of **evidence items** (project revision, artifact snapshot, responses, operational evidence, defense conversation). A **grading run** executes one exact grading pipeline — deterministic checks in a trusted runner, bounded model judgments, a defense, or human review — and records **criterion results** with explanations. An **assessment result** combines criterion results into requirement outcomes and is finalized automatically only when its policy allows; otherwise it stays provisional. Final results grant **credit** on exact requirements of the learner's adopted release; credit can carry forward only through reviewed requirement transitions (R2). **Appeals** and **reassessments** create new runs and results that supersede, never overwrite, the originals. **Mastery decisions** record evidence-based state per competency revision and facet, separately from course completion. All of it lives in the learner's own workspace; others see it only through an explicit **evidence grant** or an appeal they are reviewing.

### Reuse and source findings

- Tasks are R1 `activity` work revisions; rubrics are `decision_definition` revisions; grading, finalization, generation and mastery policies are `action_policy` revisions (approved bounded-decision kinds). Projects are Build 02 `project` works. Defense transcripts are Build 02 conversation messages. Goals are works (A3). No separate `assessment.task`/`task_version`, `learning.learner`, `learning.project`, `goal_version` or policy-version tables.
- Existing `evaluation.grader`/`grader_version`/`eval_run`/`judge_output` (source-inspected) are system evaluation records without tenant/workspace scope. They remain the place to measure grader/rubric **quality and calibration** (RV13). Learner results never go there, and those tables are not exposed to learners.
- One shared JSON contract, **`aieng.decision-answer.v1`**, describes a bounded model judgment (definition revision, requested/returned model, adapter version, input digest, status answered/insufficient_evidence/refused/timeout/invalid_result/error, typed value, native distribution/confidence, usage/cost/latency or explicit unknown, retry identity). R1 `decision_attempt` metadata and `criterion_result.judgment` both use it, so there is one decision semantics, not a course-specific copy.

## D. Behavior and invariants

1. **Presentation never grants credit.** A renderer, embedded quiz event or learner-controlled agent reporting "passed" is only input to a grading run (EDU research §3). Credit flows only from a final assessment result or a reviewed carry-forward.
2. **Facets stay separate** (U04): independent reasoning, assisted implementation and agent direction are recorded per attempt and per mastery decision; one never stands in for another.
3. **Quantity is evidence, not proof** (U05): counts, variety, time and frequency feed mastery policies as declared inputs; no universal threshold is assumed, and local thresholds are labelled unvalidated.
4. **Working systems are strong evidence** (U07/EDU-D52): official projects pin a project revision/commit and rerun checks in a platform or explicitly trusted runner; local receipts are practice evidence; deployments add operational evidence with stated limits.
5. **Explainable automatic finalization with appeal** (U08): every final result has criterion explanations and contributing evidence; abstention, insufficient evidence and infrastructure failure route to provisional, never to a silent fail.
6. **History is never rewritten.** Reassessment, appeals and rubric/test corrections create new runs/results; a correction that would lower a final result requires human review and learner notification, and the learner may appeal; corrections that only raise or confirm may finalize automatically under policy.
7. **Hidden checks stay hidden**: `evaluates_with` targets are withheld everywhere learner-visible; criterion results for them are summarized with `withheld` visibility.
8. **Optional practice never lowers completion** (EDU-D20); extensions keep separate progress; adaptations never earn the original course's credit.
9. **Privacy**: all rows live in the learner's personal workspace; course maintainers see learner evidence only through an evidence grant or an appeal they review.

## E. API additions

Commands: `start_attempt`, `abandon_attempt`, `submit_attempt` (freezes evidence; verifies digests), `withdraw_submission`, `request_grading` (system or learner rerun when a run was unavailable), `record_grading_run` / `record_criterion_results` / `record_result` (grading worker), `finalize_result` (human), `open_appeal`, `withdraw_appeal`, `resolve_appeal` (reviewer), `grant_evidence`, `revoke_evidence`, `record_mastery_decision` (policy worker or human), `create_goal`/`revise_goal` (work operations). Reads: `progress` (computed from active credits against the adopted release, with extensions shown separately), `get_attempt`, `get_submission`, `get_result` (with explanation and evidence), `list_results`, `mastery`, `goal_progress`, `appeal_status`, and `search` scope `learner_record`.

## F. Keeping current

| Subject | Trigger and change identity | Affected | User sees |
| --- | --- | --- | --- |
| Rubric/test/check corrections | New revision of a `decision_definition`, hidden-check artifact or pipeline policy bound by `evaluates_with`; identity `(binding target, old revision, new revision)` | Grading runs that used the old revision → their submissions/results | Maintainer: reassessment proposal for exact affected submissions; learner: notice and new result with explanation, original preserved |
| Grader model/adapter changes | Pinned model retired or adapter version changed | Pipelines using it | Re-qualification needed before further automatic finalization; past results unchanged |
| Runner faults | Run status `unavailable`/`error` | That submission | "Verification unavailable", automatic rerun under policy, never a fail |
| New appeal evidence | Appeal with new evidence submission | That result | Reassessment run and resolution |
| Competency/mastery policy changes | New competency or mastery policy revision | Mastery decisions | Proposed re-evaluation and review checks; no automatic loss of mastery |
| Goal revisions and new evidence | New goal revision; new credit/result | Goal progress | Updated projection and next recommended practice |

Manual and event-driven first; existing orchestration owns schedules (retention-check timing) and notifications. No watch, runner or model call is started by this schema.

## G. Scope boundaries and staged residuals

Complete in design: attempts and conditions, submissions and evidence, grading runs and criterion results, explainable provisional/final results, automatic finalization bounds, appeals and reassessment, credit and carry-forward, progress/completion views, mastery decisions with retention/transfer checks, goals, learner-granted evidence access.
